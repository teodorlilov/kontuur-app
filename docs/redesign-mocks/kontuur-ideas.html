The inbox knows which ideas are new. It just won’t say so twice the same way.

Three tabs describe four statuses. Three header counts are computed three different ways over two different scopes. The word 'new' is spelled six times across four files, 'used' five times with three different meanings — so the tab label, the tab count and the list underneath it can each disagree about the same idea. That is the whole diagnosis: this page has no shared definition of what it is showing.

The fix is not a new visual language. /clients and /review already solved grouping, tabs, tables, selection and undo. This page is the one dashboard route whose chrome was redesigned and whose content was not — commit 6b69a6d converted its inline styles to classes and preserved every original value. Below is what it looks like when it borrows from the surfaces that shipped.

01

What’s actually wrong

Correctness

Three tabs, four statuses, and no agreement on the mapping

New counts new + generating. Used counts generated + dismissed — so a dismissed idea is filed under “Used”, which is the one thing it is not. Meanwhile the settings rail counts usedCount as generated alone. Same word, two populations, one page apart.

Correctness

Three header counts, three scopes

The title count is unscoped. The tab counts are scoped to the selected client. The per-client option labels are unscoped again. Pick a client and the number beside the title stops describing what is on screen.

Interaction

Filter state that cannot be linked, shared or bookmarked

Client and status live in useState, so every idea an agency has ever received is shipped to the browser and filtered there. /clients already reads its filters from the URL and filters in the Server Component.

Interaction

A written field nothing reads

generated_post_id is stored, selected, mapped onto ClientIdea — and read by no component. Once an idea has been turned into a post, the page can say “Post generated” but cannot take you to it.

Layout

~150px of header that never compresses

The view roots at flex h-full overflow-hidden with a scrolling sibling, so StickyShell’s sentinel never leaves intersection and every group-data-[stuck=true] rule is dead. Shared with /review, /settings and /analytics.

Layout

Two dots on one row, meaning different things

A green unread dot and a per-client hue dot sit ~90px apart on the same line, neither labelled. The client hue is also indexed by list position, so a client’s colour changes when the roster does.

Craft

A bespoke class layer with no interaction states

Five hand-rolled class constants and two dead style={{transition}} objects — and zero hover: classes in the file. The buttons have no hover, no active and no focus-visible state at all.

Craft

One empty state for every situation

“No ideas yet — ideas submitted by clients will appear here” is shown to an agency holding forty of them who happens to be on an empty tab. No tab offers an action out of its own empty state.

Correctness

The idea is unreadable and uncorrectable at every step

The row truncates to one line and nothing opens. The wizard is no better: brief-list.tsx renders a committed brief as static truncated text, so the notes, platform and target date are invisible there too — and the locked idea row has no Remove. A client’s words reach the writer with no human able to read them in full, let alone sharpen them.

Craft

Zero responsive variants

The feature has no breakpoint rules anywhere. It also has no error.tsx, so a failed read renders the app-wide fallback rather than anything about ideas.

Closed already

The data layer is done

Mark-as-read is a server action that updates state, dismiss rolls back on failure, PATCH /api/ideas is deleted, the sidebar badge revalidates, and 20260817 added the FK cascades, the one-link-per-client constraint and the status/platform CHECKs. This section is only about the tab.

02

The proposal

Tabs are the states you act on. Rows are grouped by client, so the per-row client column disappears and ~150px comes back. Every row has exactly one action, and the checkboxes turn the meta line into a bulk bar. Try the tabs and the checkboxes — they work.

03

What each piece is doing, and why

Grouping by client replaces the per-row client column

When the scope is all clients, rows group under a client header. When one client is selected there is no grouping and no client column, because the page header already says whose ideas these are. That reclaims ~150px of row width for the idea text — the only column anyone actually reads — and it dissolves the two-dots problem: the unread dot becomes the only dot on the row.

The client hue moves to hashIndex per DESIGN.md, so a client keeps its colour when the roster changes.

One action per row, decided by status

new gets Generate (primary) and Dismiss (ghost). generated gets View post →, which finally reads the generated_post_id that has been written all along and links to /calendar?editPost=<id>. dismissed gets Restore. Three states, three affordances, no dead rows.

Target date is the one semantic chip

Due 12 Aug neutral, Due tomorrow in Pending, and Overdue 2d in Danger — compared against a loadedAt pinned by the server, not the browser clock. It mirrors /review’s AgeChip in behaviour, but an idea’s deadline and a draft’s review age are different facts with different thresholds, so it is a sibling component rather than a shared one.

A real table, because the columns mean something

<th scope="col"> association survives, the grid template is shared by the header row and every body row so they cannot drift, and below 1180px Platform and Target drop rather than squeeze — the same decision ROSTER_GRID already makes on /clients.

Everything else is borrowed, not invented

Card, StatusPill, Button, TabRail, SelectControl and EmptyState all exist and all carry the hover / active / focus-visible states this page currently lacks entirely. DiscardToast moves to components/ui/ on this, its second consumer, with /review’s reason chips behind an optional prop. The five bespoke class constants and both dead style objects are deleted.

04

Four calls I need you to make

1 — Does “Inbox” read better than “New”?

I have used Inbox · Generated · Dismissed · All. Each is exactly one status, which is what makes the counts trustworthy. But “Inbox” is a metaphor and the other three are literal — New would be consistent, if blander, and matches the sidebar badge’s wording.

Recommendation: keep Inbox. It is the tab people live in, and it names the job.

2 — Should bulk selection offer anything besides Dismiss?

Bulk Dismiss is clearly useful — clearing a stale inbox is the reason to have checkboxes. Bulk Generate is technically possible now that an idea is just a locked brief and the wizard accepts several. But it would fire one run per idea with no chance to set the count or add briefs, which is the opposite of what the generate flow is for.

Recommendation: Dismiss only. Generate stays a per-idea, deliberate act.

3 — Should the row open anything?  Settled: yes, read-only

The row opens a detail dialog. It earns its place on viewing alone: the idea text truncates to one line, and the notes, platform and target date are invisible without it — today they are invisible everywhere, including on the wizard’s committed brief row, which renders the title and nothing else.

It does not edit the client’s submission. The pipeline already refines a sloppy idea: the route sends idea text and notes into stage C as a REQUESTED POST, which returns a 5–10 word proper-grammar suggested_theme and a matched source. A persisted edit would be redundant for polish, and it would overwrite the only record of what the client actually asked for.

What refinement cannot fix is an ambiguous idea — the model will confidently pick a source for “the packaging thing”. That correction belongs in the wizard, scoped to one run. See §05.

4 — Do dismissed ideas expire?

Nothing ever removes a row. The Dismissed tab grows forever, and fetchIdeasForAgency currently loads every idea an agency has ever received on every page load. Pagination is already recorded as debt (TECH-DEBT §7.8), but auto-archiving after, say, 90 days is a product decision rather than a technical one.

Recommendation: no expiry now, paginate instead. Deleting a client’s request on their behalf needs a better reason than list length.
05

How it ships

  • Predicates first. Every spelling of 'new' and 'used' moves into idea-filters.ts, so the tab label, the tab count, the list filter and fetchIdeaCounts read one definition. Nothing visual changes; the numbers stop disagreeing.
  • URL-driven and server-filtered. Tabs carry an href, filtering moves into the Server Component. parseParam is extracted from clients/page.tsx on this, its second consumer; buildHref stays per-route because different params and defaults are two facts, not one.
  • The row component replaces idea-card.tsx, which is deleted in the same commit rather than left beside it. The detail dialog is the existing Modal — Radix, seven consumers already — and reads only.
  • The wizard’s committed brief becomes editable, which is where a correction belongs: scoped to one run, leaving the client’s submission intact. Today brief-list.tsx only gives fields to the draft being added; once committed, a brief is frozen text. The same edit affordance fixes the locked idea row, which currently cannot be corrected or removed. This is the one change outside /ideas, and it is what makes “view it, then fix it” a complete path rather than half of one.
  • Dismiss gets the /review treatment: optimistic removal, undo toast, commit on auto-close, restore on error, commit-pending on unmount. The server action already exists and already rolls back.
  • The sticky-header fix lands with it — the same four-line structural change on /ideas, /review, /settings and /analytics, since fixing it on one surface and not the other three would leave the app inconsistent mid-scroll.
06

Still open

  • The generating status. Nothing writes it any more, but rows written before the generate routes merged are stuck in it with no sweeper. It is still in the IdeaStatus union and in 20260817’s CHECK. Retiring it means migrating those rows to new — parked at your request, and the tab above simply has no row state for it.
  • Search is drawn but not specified. Client-side substring match over idea text is the cheap version; matching notes as well, or going to the server, is a bigger call that pagination will force anyway.
